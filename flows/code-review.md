# Code review flow

Code Review is a read-only workspace for understanding existing code with AI assistance. It is the counterpart of Diff Review for a codebase instead of a change: the same style of review workspace, scoped to the code the user chooses to explore.

The user picks a scope — a folder, or a single entry file together with the code it depends on — and the plugin loads a snapshot of the text files in that scope. Each review tab is an independent session over that snapshot, optionally narrowed to a subset of files. Within a tab, the user chats with an assistant that can only read the snapshot; it answers with citations and can place explanatory notes and source excerpts in the workspace for closer reading.

The assistant can also point to specific snapshot lines in native, read-only editors, with an optional comment. Each point opens its own side-by-side column. Chat tools follow the review context; dedicated generation commands expose their own tools only when needed.

Two generated views help navigate a large scope: hierarchical summaries describe the scope from the whole down to individual files, and topics group files by responsibility rather than by folder. Summaries and topics are tied to file contents, so they survive reloads for code that has not changed. Code decides what is read and in what order; the assistant only writes text.

Summaries and Topics both open in **Document** view, reusing Diff Review's document layout with complete source files in place of diffs. Every file in the tab's scope appears once in one long, read-only document, with line numbers and its summary alongside it. Summaries follows the file tree and shows cards with the full file paths, together with folder and group cards. Topics orders the same files by topic and shows topic cards spanning their files; files still awaiting a topic remain visible at the end. Files summarized in parts are still displayed as complete files. Level controls limit the cards shown without hiding source files, and document zoom and sticky headings help with long scopes. The summary outline and file and topic hierarchies remain available through the view switchers.

The Summaries outline always shows file and folder names, with metadata and file actions on the same header line. Clicking a summary expands or collapses its children, like its arrow; scored words retain their context and search actions. Selecting text in a summary and choosing Search from its context menu runs the same search for the selection, without needing Score first. File and part summaries are scored too: clicking a highlighted word in one scores the blocks of the file's source against the word's query, then the lines of the best block, and opens the file scrolled to those lines with them highlighted. Outline and Hierarchy show scoring and hover status in a fixed footer so hints do not move the summaries.

**File view** shows the functionality behind the calls in one file. Select a file in the file tree and click View (or Open in File View in its menu). The file is split into blocks — its outermost functions and properties, adjacent properties together, and the lines between them — and shown top to bottom in the same document layout. The right rail shows topic cards for the neighboring files called by each block. Each call stops at the first other project file; helpers inside the viewed file are followed until they cross that boundary. Hover a source line to see only its neighboring files' topics and summaries in the left margin, or hover a topic card to see its neighboring files' summaries and highlight the corresponding call lines. Summaries disappear when the pointer leaves. The viewed file's own summaries and topics are excluded. Files without a topic or summary yet have placeholder cards, with Classify and Summarize to fill them in; neighbors outside the review scope are identified without generated text. Calls are resolved statically and are not runtime order. Local helper traversal has depth and size limits, and the view follows edits to the scope.

Entry points for further exploration:

- [CodeReviewPanel.kt](../src/main/kotlin/dev/insight/codereview/CodeReviewPanel.kt) — tool window entry point: scope selection, file tree, and review tabs
- [CodeReviewTab.kt](../src/main/kotlin/dev/insight/codereview/CodeReviewTab.kt) — per-tab session: chat, workspace, summaries, and topics

From there, neighbouring files in the same package cover loading, tools, and state; shared workspace and summary machinery lives with Diff Review.

Summaries, topics, topic hierarchy texts (Fill summaries), and word scores are saved in `.insight/review-cache/` in the project directory and survive IDE restarts, one slot per scope. Entries are keyed by content, not by the whole snapshot: a summary by its node key, which covers every file and part beneath it, a topic by its file’s path and content hash, and a word score by its full judgment request. An edited file regenerates only its own results and those of the folders, groups, topics and root above it; the rest of the scope is restored. A slot also keeps entries of earlier snapshots, oldest dropped first. Partial runs are saved so they can continue. Regenerate drops the saved entries of that kind. The directory is excluded from code scopes and contains its own Git ignore file; delete it while the IDE is closed to clear the disk cache.
